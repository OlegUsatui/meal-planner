# Architecture

Meal Planner is a React/TypeScript PWA with Vercel REST Functions in front of Supabase. `src/app` owns shell, routes, auth gating, and providers; `src/features` owns product, recipe, meal-plan, shopping, and account capabilities; `api/` owns authenticated HTTP handlers; `src/api/` owns browser repository clients; `src/supabase` owns the server-side Supabase adapters used by those handlers; `src/db` retains legacy local backup/import code for compatibility and isolated domain tests; `src/shared` contains reusable UI and formatting. Supabase profiles carry the `user`/`admin` role, and both API checks and database RLS enforce admin permissions.

Repositories isolate the API from React. The browser Supabase client is used only by AuthProvider to obtain and refresh the session. API clients send the access token as `Authorization: Bearer ...`; each Vercel Function creates a request-scoped Supabase client with `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, so Supabase Auth and RLS remain the authorization boundary. Domain calculations are pure. The shopping API reads products, recipes, ingredients, and the current user's plan and returns a derived projection without writes or cache state.

Private browser reads use one TanStack Query v5 in-memory cache per authenticated user. Query keys always include the user ID; the session cache is cleared on logout, session expiry, user change, and provider unmount. It is never persisted to IndexedDB, the Service Worker, or the browser HTTP cache. Catalogue/detail data is fresh for five minutes; dashboard, visible meal-plan ranges, and shopping ranges are fresh for 30 seconds and may refresh in the background while retaining stale successful data. Garbage collection is 30 minutes. Reads retry once only for network/5xx failures, and searchable/ranged requests forward `AbortSignal` to `fetch`. Repository objects are memoized for the session so React renders cannot restart reads through changed object identity.

All successful API responses use `{ data: ... }`; failures use `{ error: { code, message } }`. HTTP responses remain `Cache-Control: private, no-store`. Recipe catalogue reads are server-paginated and return lightweight `RecipeSummary` records plus page metadata, with search and taxonomy filters applied before the database range. Summaries exclude instructions, nutrition, and ingredients; `/api/recipes/:id` is the only full-recipe read. `systemOnly=true` restricts onboarding reads to shared recipes. Lists return stable public R2 URLs for system images and presigned R2 GET URLs for personal images. Recipe writes request an R2 presigned upload URL, upload the image directly from the browser with `PUT`, and then send only image metadata to the API. Upload paths are checked against the authenticated user's ID before metadata is persisted.

The shell is mobile-first and owns route focus, online/offline status, install/update prompts, global recovery, navigation, and shared feedback. Server-backed feature screens retain stale successful data when a refresh fails and expose an explicit retry. The app shell is available offline, but authentication and all server data mutations require connectivity.

Profiles persist onboarding completion. Dashboard, ranged meal-plan, and ranged shopping endpoints return only the data needed by their visible horizon. Account export returns a versioned manifest and short-lived private image URLs; the browser packages the export. Account deletion is authenticated, explicitly confirmed, removes private image objects, and then deletes the caller through a narrowly scoped database function.
