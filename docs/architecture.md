# Architecture

Meal Planner is a React/TypeScript PWA with Vercel REST Functions in front of Supabase. `src/app` owns shell, routes, auth gating, and providers; `src/features` owns product, recipe, meal-plan, shopping, and account capabilities; `api/` owns authenticated HTTP handlers; `src/api/` owns browser repository clients; `src/supabase` owns the server-side Supabase adapters used by those handlers; `src/db` retains legacy local backup/import code for compatibility and isolated domain tests; `src/shared` contains reusable UI and formatting.

Repositories isolate the API from React. The browser Supabase client is used only by AuthProvider to obtain and refresh the session. API clients send the access token as `Authorization: Bearer ...`; each Vercel Function creates a request-scoped Supabase client with `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, so Supabase Auth and RLS remain the authorization boundary. Domain calculations are pure. The shopping API reads products, recipes, ingredients, and the current user's plan and returns a derived projection without writes or cache state.

All successful API responses use `{ data: ... }`; failures use `{ error: { code, message } }`. Recipe catalogue reads are server-paginated and return page metadata, with search and taxonomy filters applied before the database range. They return stable public R2 URLs for system images and presigned R2 GET URLs for personal images. Recipe writes request an R2 presigned upload URL, upload the image directly from the browser with `PUT`, and then send only image metadata to the API. Upload paths are checked against the authenticated user's ID before metadata is persisted.
